# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Study Reader is a PySide6 desktop PDF/EPUB/web-page reader (Linux only) where selected passages or screenshot regions are sent to per-snippet Claude chats that all share the whole book as context. See README.md for user-facing behavior and keyboard shortcuts.

**Terminology:** the UI says **question** (any type; never "card"), **practice** (the Practice page, a session, the act), **attempt** (one logged rating), **deck**, and **message** (what the user sends Claude in a chat; buttons say "Ask"); spaced repetition is never named. Code follows: `questions`/`question_id`, `practice.py`/`PracticePanel`/`practice_*` settings, `attempts`/`attempted_at`/`last_attempt`/`record_attempt`, `Job.message`, and `question_groups`/`group_id` for the hidden group of sibling questions sharing fields. Types (`question_model.TYPES` → `TYPE_LABELS`): `self_check` Self-check, `both_ways` Self-check (both ways), `fill_in` Fill-in-the-blank, `image_labels` Image labels, `choice` Multiple choice, `truefalse` True/false, `calculation` Calculation, `short_answer` Short answer. Ratings 1–4: Missed / Shaky / Got it / Easy (`quiz.RATINGS`); `stage` 0–3: New / Learning / Learned / Relearning (Young and Mature are kinds of Learned). Old names stay only where they are someone else's: py-fsrs's API and JSON (`Card`, `ReviewLog`, `Rating.Again`…`Easy`, `State.Review`, `review_card`, `card_id`/`last_review` inside the `fsrs` column; `android/core/…/Fsrs.kt` ports it as is), Anki's concepts in `anki_import.py` (notes, cards, revlog, `NoteType`), the field syntax `{{c1::…}}` and `image-occlusion:` and the `.cloze` CSS class, the bookless chats' cwd `<data>/sessions/cards` (renaming it would orphan sessions), visual cards (`.card` panels, the Library's `_BookCard` tiles), the user's Notes (`notes.py`, unrelated), and the aliases and migrations that read old data (`question_model.KIND_ALIASES`, `quiz.TYPE_NAMES`, `search.TYPE_ALIASES`, `gamify.ACHIEVEMENT_ALIASES`, `browser.OLD_COLUMNS`, `db.SETTING_RENAMES`, `Database._rename_old_schema`, phone batch format 1). New code, comments and UI text use these words.

## Commands

Pixi manages the environment; `PYTHONPATH` is set to `src/` by pixi activation, so run everything through `pixi run`.

```sh
pixi run app [book.pdf | URL]      # launch (library screen, or open a book or web page)
pixi run test                      # pytest -q tests
pixi run pytest -q tests/test_core.py::test_first_chat_primes_then_forks   # single test
pixi run check-claude              # live priming+forking check; makes real Claude requests
```

Tests never hit Claude: `FakeClaude` in `tests/test_core.py` monkeypatches `claude_client.run_turn` and `claude_client.session_exists`. Test PDFs/EPUBs are generated on the fly in `tests/conftest.py`.

## Architecture

**Shared book context via session forking** (the core idea, spread across `claude_client.py` and `chat_service.py`):
- Claude is reached through the Claude Agent SDK (`query()`), which drives the local `claude` CLI and its login. Each book gets its own session working directory (`<data>/sessions/book-<id>`), since SDK sessions are scoped by `cwd`.
- The first question for a book "primes" a base session containing the full extracted text (`[[page N]]` markers). Each new chat resumes that base session with `fork_session=True`; follow-ups resume the chat's own session without forking.
- `ChatService.ask` decides the route: chat session exists → resume it; otherwise `ensure_base` (re-priming if the base session was pruned) then fork, replaying saved DB history as a transcript if the chat's own session was lost.
- Regenerate / edit truncate the chat in the DB, then branch: each assistant message stores its `session_id` and `session_uuid` (last transcript entry), and the job resumes that session with `resume_at` (SDK `resume_session_at`) plus `fork=True`. With no usable branch point the job falls back to fork-from-base plus history replay, and `ask` retries that way if the branch point fails to load.
- Books over `MAX_BOOK_TOKENS` (estimated at 3 chars/token), or whose priming fails with a "too long" error, switch to `context_mode="partial"`: no base session, and each question carries a `text_window` of pages around the current page.
- Chat titles: a chat started from the composer is named after its first question until its first reply lands; then `ChatPanel._name_chat` asks `ChatService.title` for a short title (`cc.chat_title`: a fresh, bookless Haiku session under `<data>/sessions/titles` with `TITLE_PROMPT` as its system prompt). The `titled` event only applies if the chat wasn't renamed meanwhile; failures are silent. Quiz chats keep their given titles.
- `_options()` deliberately strips all tools, MCP servers (including claude.ai connectors via `ENABLE_CLAUDEAI_MCP_SERVERS=false`), and setting sources, and uses `max_turns=1`. `_prefer_subscription_login()` removes `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN` from the environment unless `STUDY_READER_USE_API_KEY=1`.
- A resumed or forked session keeps the system prompt it was created with; the `system_prompt` passed on later calls is ignored. So `SYSTEM_PROMPT` edits only reach newly primed books. Put behavior that must apply everywhere in `READER_INSTRUCTIONS`, which `build_blocks` sends with every question.

**Threading:** `ChatWorker` runs `ChatService` on a dedicated asyncio loop in a daemon thread. `ChatService` is Qt-free and reports through an `emit(name, *args)` callback; `ChatWorker._emit` maps names to Qt signals (`status`, `base`, `delta`, `done`, `failed`) that `ChatPanel` connects to. Keep new events in both places. Persisting results (session ids, `context_mode`, messages) happens on the GUI side in `ChatPanel`, not in the service.

**UI modules:**
- `main_window.py` wires everything: the navigation rail (`nav.py`'s `NavRail`, with the Settings menu at its foot) beside a center `QStackedWidget` of pages (`MainWindow.pages`: home, library, practice, questions, stats, and "book", the reader), the reader's toolbar (shown only while reading), TOC dock, highlights → chat navigation. `show_page` switches pages; the open book stays open behind the others (`close_book`, `Ctrl+W`, closes it), and `reading` means the reader is on screen, which gates the toolbar, book actions and right-hand panels. The question browser (`QuestionBrowser(embedded=True)`, a `QMainWindow` used as a widget, its menu bar inside the page) and statistics (`StatsWindow(window=False)`) are made on first visit into `_Page`s. While Questions is shown, the window's Open web page action is disabled so the browser's `Ctrl+Shift+O` wins; page shortcuts are `Alt+1`–`6` because the browser uses `Ctrl+digits` for flags.
- `home_view.py`'s `HomeView` renders `assets/home.html` from `dashboard.home()` (Qt-free `dashboard.py`: per-book counts `book_counts`, the Practice page's deck list `deck_rows`, `reading`, `heat`, `forecast`). Covers are first-page PNGs in `<data>/covers/<hash>.png` (`covers.py`); the Library and Home (`HomeView._draw_cover` → `setCover` in `home.html`) draw them a turn of the event loop at a time. `assets/app.css` (panels, buttons, the due/new colors) and `assets/progress.js` (rewards row, calendar heatmap, forecast bars) are shared by `home.html` and `practice.html`; `stats.html` loads `progress.js` for its calendar. Theme keys `new`/`new_soft` (blue: new questions), `success_soft`, `rail` and `shadow` reach pages as CSS variables like the rest.
- `reader_view.py` is a custom `QAbstractScrollArea` that renders pages with PyMuPDF, handles word-level text selection, region screenshots, persistent highlights, and the flash-on-jump effect.
- Find (Ctrl+F): `book_search.py` (Qt-free) folds each page's words (`Document.search_words`: reading order if `words` has already worked it out, else PyMuPDF's, since ordering is most of the cost) into one string (case, accents, ligatures, curly quotes folded; line-break hyphens joined), keeping each word's offsets and, where folding changes a word's length, a char map, so matches turn back into per-line rects (partial words cut in proportion) and printed context. `BookSearch` scans from the current page to the end, then from the start, a time-boxed `step` at a time (a step never crosses the wrap, so its matches are inserted together into the page-ordered list); `SearchIndex` caches folded pages per open book. `find_view.BookFind` runs it on a zero-interval `QTimer`, owns the `FindBar` (floating in the reader's viewport) and `FindResults` (a `QListView` swapped for the TOC in the sidebar's `side_stack` while active; `MainWindow._sync_sidebar`), and paints matches through `ReaderView.set_find`/`show_match`. `ReaderView.escapePressed` (Escape with no selection) closes it.
- `chat_panel.py` holds the chat list, composer, and per-chat model selector, and builds `Job`s for the worker. There are two `ChatPanel`s: the reader's (`MainWindow.chat`) and the Practice page's (`MainWindow.practice_chat`, `practice=True`), sharing a `ChatHub` (replies on the way and the panel that asked for each: only the owner handles a chat's `delta`/`done`/`failed`, every panel showing the chat draws the stream, and `_changed` tells the other panel to refresh; also the short answers being graded, `ChatHub.grading`, and `_update_quiz` redraws a quiz in every panel showing its chat). The Practice page's panel takes turns with its calculator in `practice_right` (F10 `practice_chat_action` / F11, one at a time, the `practice_panel` setting; the older `practice_calc` setting is read once) and follows `PracticePanel.questionChanged` while open: `set_question(PracticePanel.chat_question())` brings up the question's latest chat (`chats.question_id`, `Database.question_chat`), else its quiz chat, else a new chat (not focused, so practice keeps the keyboard), switching to the question's book's chats (`book_id` None: chats about questions with no book, run in the bookless `sessions/cards` cwd, resumed or replayed like book chats). While a question is attached (`_question_attached`: a new chat, one about the question, or its quiz chat; the **Question** chip removes it until the next question) `quiz.question_context` goes in `Job.context`: the question as shown (unlettered choices, since practice shuffles them) and, until the answer is shown, a request not to give it away. Its **Chat** button in `practice.html` comes with `o.chat_panel`, never sent by the phone; a question's **Open chat** (`chatRequested(chat_id)`) opens the quiz chat in this panel. Throwaway chats (`chats.throwaway`, the header's ghost toggle, `ChatPanel._throwaway` for new chats) are left out of `Database.chats`, make no questions and get no title, and are deleted with their Claude sessions (`ChatWorker.forget_sessions`, `cc.forget_session`) whenever the panel leaves them (`_leave`), on quit (`close_throwaway`) or at startup (`drop_throwaway_chats`); **Save chat** clears the flag, makes the questions and names it. Stop: while the open chat streams, the send button (and Esc) stops it: `ChatWorker.stop` cancels the `ask` future (`run_turn` closes the SDK stream with `aclosing`, so the CLI exits; nothing more is emitted), and the owner saves the text so far as a reply with `messages.stopped`; the next message carries `quiz.stopped_context`.
- `calculator.py` has a Qt-free `Calculator` (safe `ast`-based evaluator; never `eval`; ints and decimals stay exact as `Fraction`s, functions give floats) and the `CalculatorPanel`. There are two: the open book's shares the right-hand `QStackedWidget` slot (F11; it replaces chats and notes), and the Practice page's (`MainWindow.practice_calc`, `shared=True`, beside `MainWindow.practice` in `practice_page`, a splitter) is toggled by its own F11 action (`practice_calc_action`, enabled only on that page while `calc_action` is enabled only while reading; open state in the `practice_panel` setting). The Practice page's follows `PracticePanel.questionShown` (the book of each question drawn): that book's history, or for a question with no book the shared history (`calculations.book_id` NULL). The Practice page draws a **Calculator** button (overview header and question bar in `practice.html`) only when the payload carries `calc` (`PracticePanel.set_calculator`, kept in step with `practice_calc_action`; `setCalc` lights it), which the phone app never sends; clicking it emits `calculatorRequested`. Each calculator's `historyChanged` makes the other `reload()` (input kept) when it shows the same history. The panel's history and input are `assets/calculator.html`: a MathLive math field (bundled in `assets/mathlive/`) talking to `_Bridge` over `QWebChannel`. `calc_latex.py` turns the field's LaTeX into plain expressions (inserting implied multiplication) and results back into LaTeX/fractions. History is per book (plus the shared one) in the `calculations` table (`expr` evaluated, `latex` as typed); `ans` and variables are restored from stored values, not by re-evaluating.
- `transcript_view.py` is a `QWebEngineView` loading `assets/transcript.html` (markdown-it + KaTeX, bundled offline in `assets/`). Snippet clicks come back as `jump:<snippet_id>` navigations intercepted in `_Page.acceptNavigationRequest`.
- Visualizations: `READER_INSTRUCTIONS` tells Claude to write ```` ```visualization <title> ```` fences of self-contained HTML/JS. `transcript.html` renders each fence in an `<iframe sandbox="allow-scripts" srcdoc>` built by `vizDoc()`. That doc carries a no-network CSP, the theme as CSS variables plus `vizTheme`, and d3/Chart.js inlined from `assets/viz/` when the code references them (sandboxed frames can't load `file://`). Frames `postMessage` their size (`vizSize`, with the width it was measured at) and `assets/vizfit.js`'s `VizFit` fits each into the panel: laid out narrower when too tall (plots drawn to the width shrink with it), then scaled. During streaming, fences show a placeholder. `viz://open/<n>` opens `VisualizationWindow` with `vizDoc(n, true)`, fetched via `runJavaScript` as JSON: `assets/vizwindow.html` is a toolbar over a full-window frame whose doc runs `vizWindowMode` (inlined by `vizDoc`), which moves the controls into a pinned dock outside the body, fits the body and zooms it with CSS `zoom`; the toolbar talks to it by `postMessage`, and F11/Escape come back as `viz://fullscreen`/`viz://normal` navigations.
- Quizzes: `READER_INSTRUCTIONS` also defines ```` ```quiz <title> ```` fences of JSON (types choice, truefalse, calculation, short_answer, and self-rated self_check; flashcard requests are quizzes of self-checks). `quiz.py` (Qt-free) parses them (forgiving undoubled LaTeX backslashes; `quiz.TYPE_NAMES` also reads the old type names, flashcard, numeric, written and the older `"free"`, which older replies hold, for good), grades choice/true-false/calculation answers locally (calculation through `Calculator`), and builds the grading prompt and the `<quiz_answers>` context (`Job.context`) sent with later messages. Quiz me (`ChatPanel.start_quiz`, `quiz_on_reply`) sends nothing: it drafts the request (`quiz.request`/`snippet_request`/`reply_request`) in the composer, setting its contents aside like an edit, and keeps the scope (title, pages, snippet) in `ChatPanel._quiz`, shown as a removable chip; the next send makes the quiz chat (with its given title, so it is never renamed; none is made if the draft is dropped) and sends `quiz.drafted_request` (the composer text if it still holds the request, else the request plus what was typed). Removing the chip, Esc, or leaving the chat (`cancel_quiz`) drops it. `ChatPanel` replaces each fence with a `#<index>` placeholder plus parsed data that `transcript.html` renders; answers come back over a `QWebChannel` (`_QuizBridge`) and are stored in `quiz_answers`. Short answers are graded by `ChatService.grade` as a `detached` job that always forks (at the quiz reply's `session_uuid`), so the chat's own session never sees it. `assets/mathfield.js` holds the MathLive setup shared with the calculator.
- Practice: every quiz question goes into practice. `practice.py` (Qt-free) makes questions from a reply's quiz fences when `ChatPanel` saves it (`add_quiz_questions`; one per `message_id, quiz, position`, in the book's deck, `books.deck_id`, made by `Database.book_deck`), and schedules them with the `fsrs` package (`questions.fsrs` holds the `fsrs.Card` JSON, `stage` 0 = new, else `fsrs.State`; `stability`/`difficulty`/`last_attempt` mirror it for browsing, so write schedules through `practice.schedule_columns` (`practice.new_schedule_columns` for new questions); retrievability from those columns is `practice.recall`; `practice.attempt` schedules a rating, and `attempts` logs each with its `duration`; `attempt` and `previews` go through `practice._review`, which seeds py-fsrs's fuzz from the question id and `reps`, so the previewed interval is the one scheduled). `practice.scheduler(db)` uses the stored FSRS weights (`practice_parameters`, from Anki or `practice.fit` over `practice.attempt_logs`, which needs PyTorch, installed CPU-only by pixi) and desired retention. The first answer in the chat is a question's first attempt (`answered_in_chat`, verdict → rating; self-checks are rated directly); retakes don't count. Learned questions (`stage` 2) are due for the whole day they fall on (days roll over at 4 am); new questions are capped per day across all decks (`practice_new_per_day`). Deleting a reply drops its never-attempted questions; attempted ones outlive it with `message_id` NULL (`Database._drop_new_questions`). `practice_view.py`'s `PracticePanel` (rendered in `assets/practice.html`, web channel object `practice`; one, `MainWindow.practice`) is the Practice page, with a deck tab and a book/section tab picking `PracticePanel.picks`: any number of `{"deck": id}` (subtree via `db.SUBTREE`) and `{"book": id, "section": tag or None}`, practiced as their union (`picks=` on `practice.counts`/`next_question`/`next_due`/`left_to_practice` and `Database._scope`; empty is every question). `practice.html` sends the whole list through `bridge.choose` (click picks one row, Ctrl+click toggles, Shift+click a range from `ANCHOR`, a long press toggles on the phone); `PracticeController.picks`/`Practice.Pick` mirror it on the phone. There is no in-book practice: F8 and the reader toolbar's **Practice** (showing the open book's count; `practice_open_book`) call `MainWindow.practice_book` for the open book, as the Library's and Home's per-book **Practice** do (the Practice page narrowed to it, a session started). Short answers are graded by Claude only in the chat; in practice they are self-rated like self-checks (an optional answer box, then the model answer and rubric beside it; `selfRated` in `practice.html`), and `READER_INSTRUCTIONS` keeps them as a last resort. Question rendering is shared by `transcript.html`, `practice.html` and `questionview.html` in `assets/quiz.js`/`quiz.css`. `practice.backfill` makes questions once for quizzes written before there were any. New numbers: after a calculation or short-answer question's attempt (or first answer in the chat), `practice_view.VariantMaker` (one, made by `MainWindow`, handed to `ChatPanel` and the `PracticePanel`) asks for the problem's next version with fresh givens (`variants.request`, in a fresh bookless session to keep it cheap, via `ChatWorker.submit_variant`, `varied`/`variantFailed` events) and stores it in `questions.variant` (`{"skip": true}` when Claude says there is nothing to vary, kept only for questions that may skip, `variants.may_skip`: for multiple-choice and `"varies": true` ones a skip is dropped and asked again next time). Quiz questions carry `"varies"` (from `READER_INSTRUCTIONS`, or the browser editor's checkbox); `false` means never ask, `true` tells Claude to rephrase rather than skip, and only unmarked older questions get the one-time check; the `variants` setting (`variants.ENABLED_SETTING`) turns new versions off everywhere, and practice and the phone snapshot then show the questions as written; practice shows `variants.question(row)`, pinned while the question is up. Edits that change a question's data drop its variant. Multiple-choice questions (`variants.TYPES`) are varied too, by `variants._choices_request`: new choices only (right answer reworded, new wrong ones), never skipped, and `variants.parse` keeps the question's own text; `"varies": false` on one comes only from the browser's checkbox (`READER_INSTRUCTIONS` doesn't ask for it). Practice also draws a choice question's options in a new order each time it comes up (`choiceOrderFor` in `practice.html`, so the phone too; `choiceOrder` in `quiz.js` keeps "none of the above" in place and doesn't mix options named by letter). Only the drawing is mixed: `bridge.check` and the attempt log get indices into the question's own `choices`. Chat quizzes keep Claude's order.
- Section and concept tags: `add_quiz_questions` tags each question `Book::Chapter::Section` (`practice.section_tag`, parts cleaned by `question_model.tag_part`) from the book's TOC, stored as JSON in `books.toc` by `practice.learn_toc` (called in `open_book`; at startup `MainWindow._learn_tocs` opens books with quiz questions but no stored TOC). The page comes from the snippet or from `messages.page_from`/`page_to` (a quiz on a page range gets the common prefix of both ends' section paths); learning a TOC the first time tags that book's existing questions. Back matter (Summary, Exercises…) that a TOC nests in a chapter's last section is filed under the chapter (`practice._entry_path`), and a question may name the section it practices (`"section": "6.4"`, matched by `practice.find_section`), which wins over its page, so end-of-chapter exercises land in their sections. Questions may carry their own `"tags"` (concept tags, cleaned by `question_model.clean_tag`); `practice.tags_context` sends the user's existing concept tags (`<existing_tags>`, capped) in `Job.context` with every message so Claude reuses them. The Practice page can narrow to a book or a section (`practice.sections` builds the per-book tree in reading order, by each section's TOC start; a `{"book", "section"}` pick narrows `counts`/`next_question`/`next_due`, and `Database._scope` takes `tag=`, matching the tag and its children); a narrowed session shows due and new questions only. Books' own decks are left out of the deck picker unless a user deck sits under them. The browser sidebar orders section tags by page and has a tag filter (`Sidebar.filter_tags`).
- Quiz revisions: a quiz fence may name the quiz it `"revises"` (by title; `quiz.revised_quiz` falls back to the chat's latest quiz), and each question the 1-based number of the old question it replaces. `add_quiz_questions` moves those questions to the new reply (`Database.relink_question`) and rewrites their fields (`update_question_group`, merging tags), so their attempts stay; then `Database.drop_new_quiz_questions` removes the old quiz's remaining never-attempted questions. The **Revise…** button (`_QuizBridge.revise` → `ChatPanel.revise_quiz`) sends `quiz.revise_request`; `ChatPanel._revisions` maps old quizzes to their revising reply so `transcript.html` dims them with a "Show the revision" link. Regenerating a revision reply loses the questions it took over that were never attempted.
- Rewards: `gamify.py` (Qt-free) gives the Practice page XP and levels, a combo (questions in a row without a `COMBO_PAUSE`; it raises the XP multiplier), a daily goal, streaks with streak freezes, achievements, quick sessions (`Session.limit` "questions"/"time") and session summaries. XP never depends on the rating, so it never pays to rate a question better than it went. Streaks and today's count come from the attempt log; XP, freezes and unlocked achievements live in the `gamify_state` setting (made from the log the first time; achievement keys from before the rename, `reviews_100` and so on, are read through `ACHIEVEMENT_ALIASES`/`achievement_key`). `PracticePanel` sends what an attempt earned to `celebrate()` in `practice.html` (toasts, `assets/confetti.js`); the `gamify` setting hides it all.
- Decks and question types: questions belong to `decks` (full `A::B` names; parents have rows). Every question has one of a flat list of types, `question_model.TYPES` with `TYPE_LABELS` (self_check, both_ways, fill_in, image_labels, choice, truefalse, calculation, short_answer), used by the editor, the Add dialog, the browser's sidebar, Type column and `type:` search, and the Anki import. A question's type is its `question_groups` row's `kind`; that row (JSON `fields`, Anki-style tags ` a b `) is internal and never shown as such: it groups sibling questions that share fields and tags (a fill-in-the-blank's numbers, a both-ways self-check's two sides, image labels' shapes; `question_ords`), and UI text speaks of questions and says when an edit reaches the siblings. The four `QUESTION_TYPES` hold the question as `quiz.py` parses it, with its `type` equal to the kind; a self-check from a chat quiz is a `self_check` (`question_model.question_fields`). Each question's JSON (`question_data`, cached in `questions.data` and remade by `Database.update_question_group`) has `type` equal to the kind, except a `both_ways` one's, which draws as `self_check`. `Database._migrate_question_types` moved older kinds (basic, reverse, quiz, then Anki's flashcard, reversed, cloze, occlusion and numeric, written, `"free"`: `question_model.KIND_ALIASES`) in fields, data and variants over. Self-checks, fill-in-the-blanks and image labels are self-rated (`question_model.SELF_RATED`, `quiz.js` `SELF_RATED`); in practice, short answers are too. Question text is Markdown that may hold inline HTML (`q.html`), rendered by `renderMarkdown(…, rich)` in `markdown.js`, which rebuilds it from an allowlist of tags, attributes and URL schemes (pages with web channels must never run scripts from question text) and points relative image paths at `media_dir()`; the editor sets `html` on the questions it saves, while chat-quiz questions stay plain until edited. Databases from before decks are migrated by `Database._migrate_questions_to_groups`, which rebuilds `questions` with foreign keys off; indexes live in `INDEXES`, applied after migrations.
- Question browser: `browser.py`'s `QuestionBrowser` window (made lazily by `MainWindow.show_browser`) runs `search.py` (Qt-free Anki-style query → SQL over `search.FROM`; `SORTS` per column) into `QuestionTableModel`, which reads rows a chunk at a time. Column widths are worked out by `QuestionBrowser._fit_widths` on every viewport resize: compact columns fit their header and `SAMPLES`, `FLEX_COLUMNS` share the rest by weight within bounds; a column the user drags keeps its width (`browser_widths`), and a dragged column's new place becomes the saved column order (column ids saved by older versions go through `OLD_COLUMNS`). `question_editor.py` holds the `QuestionEditor` (autosaved after a pause; its type box switches among self_check, both_ways and the question types, `SWITCHABLE`) and `AddDialog`. Switching a question's type carries its text over (`QuestionEditor.switch_type`: a self-check's front/back/extra are a question's question/answer/explanation, and answers carry between question types); an edit that can't be saved yet is kept per `question_groups` row in `QuestionBrowser._drafts` and shown again when one of its questions is, so leaving the question doesn't revert it. `search.TYPE_ALIASES` keeps old searches working (every older type name, plus `quiz`, and `note:` for `type:`; `is:review` is `is:learned`). `questionview.html` (`QuestionView`) shows the preview's read-only question sides (and Make with Claude's draft). `stats.py`/`stats_view.py`/`stats.html` are the Statistics window.
- Make with Claude: `deck_maker.py` (Qt-free; its docstring is the design) holds one draft (`deck_drafts`, at most one row; `draft_batches`, one per request with its Claude session; `draft_items`, each question numbered `#n` for the user and Claude). Mode `new` makes a deck from a description plus optional notes and files (`new_blocks`; files stay a `source_files` block that `expand_files` reads off the GUI thread in `ChatService.make`: documents' text through PyMuPDF, text files, images attached; at most `MAX_SOURCE_CHARS`); Claude names the deck (under the chosen parent) and decides the count (at most `MAX_NEW` a reply). Mode `improve` (what Convert with Claude was) sends existing questions in batches of `BATCH_SIZE` (`improve_blocks`, `existing_payload`); each is rewritten, split (up to `MAX_SPLIT`) or kept, and `needless` keeps answered questions from becoming self-checks. Questions travel as `QUESTION_FORMAT` JSON (quiz question objects plus `self_check`, `both_ways` and `fill_in`), stored as specs `{kind, fields, tags}` (`question_spec`, `for_claude`; `parse` still reads replies that say `cards`). Replies are actions (`add`, `rewrite`, `keep`, `remove`; `parse`, `record`); follow-ups (`follow_up_blocks`) send the draft as it stands, ticked or not (`draft_state`), go only to the batches holding the questions they name by `#n` (`follow_up_targets`; one naming none goes to every batch, and the window asks first when that's more than `ASK_OVER`), resume the batch's session, and fall back to its first request plus the follow-up when the session is gone (`ChatService.make` gets both). Only a draft's first batch may add new questions (`is_first_batch`). `apply` adds the ticked new questions to the draft's deck and runs `rewrite` on ticked existing questions (`Database.move_question_to_group`, schedule kept, extra fill-in/both-ways questions and a split's others made new, the old state in `question_rewrites` for `undo_rewrite`). `deck_maker_dialog.py`: `DeckMaker` (made by `MainWindow`, handed to the browser; `ChatWorker.submit_make`, `made`/`makeFailed` events, at most `MAKING_AT_ONCE` together, model per draft, Sonnet by default) and `MakeWindow` (the request forms, then the draft drawn by `showDraft` in `questionview.html`, each item's `groups` the proposed question groups, whose checkboxes call `QuestionView`'s optional bridge; a change of ticks alone goes through `setTicks` without a redraw). Entry points: Home's header (`HomeView.makeRequested`), the Practice page's deck picker and empty state (`PracticePanel.make_link`, desktop only, so `o.make` never reaches the phone), the browser's **Claude** menu (`Ctrl+Shift+M` make, `Ctrl+Shift+K` improve, undo) and deck context menu.
- Anki migration: `anki_import.py` (Qt-free) reads a temp copy of `collection.anki2` (decoding the protobuf blobs it needs), maps Anki's note types to question types by their fields (`NoteType.kind`), converts field HTML to Markdown (`to_markdown`), imports schedules, revlog (as attempts with source `anki`), media and FSRS parameters; `questions.anki_id`/`question_groups.anki_id` make re-runs skip what's there. `anki_dialog.py` is its dialog. It never writes to Anki.
- Notes: `notes.py` has Qt-free search/Markdown export and the `NotesPanel`, one of the panels in the right-hand `QStackedWidget` (`MainWindow.right_panels` maps `books.right_panel` names, `chat`/`notes`/`calc`, to their toggle actions; at most one is shown, `''` for none). Notes render in `assets/notes.html` and edits come back over `QWebChannel`. Notes live in the `notes` table (passage text + rects, like snippets) and are passed to `ReaderView.set_highlights` alongside snippets; a mark holding notes draws in blue. They are never sent to Claude. `notes.html` sends unsaved edits as they are typed (`draft`), and `NotesPanel.flush` saves them when the book changes or the app closes. `assets/markdown.js` holds the Markdown + KaTeX rendering shared with `transcript.html`.
- Read aloud: `speech_text.py` (Qt-free) turns text into what is spoken (`tex_to_speech`, `math_symbols`, `speak_word` abbreviations), splits sentences (`ends_sentence`), and maps an engine's timed tokens onto the spoken text (`align_tokens`); an `Utterance` keeps its page rects and `marks` (spoken char range → page rects) so a word timing lights the right word. `speech_pages.BookText` (Qt-free, per `Document`, lazy a page at a time on the GUI thread) yields a book's sentences from a word on, skipping running headers/footers/page numbers (edge lines repeating on p±1/p±2), footnotes (`footnote_starts`: a raised marker opening a row, so numbered steps, bullets and wrapped exponents aren't taken for one and everything below them skipped; footnote links, numbers glued after punctuation) and captions, joining hyphenation, finding headings by font size (`Document.body_size`) and speaking web snapshots' tiny `.tex-src` runs as math. `tts_engines.py`: `KokoroEngine` runs Kokoro in a spawned process (`kokoro_worker`, niced, exits when the app does; started by `warm()` when a book opens, since loading takes seconds). Jobs carry a generation (shared `Value`) so cleared ones are skipped; results come back through a listener thread and `_Bridge` signals into a `PcmQueue` pulled by a `QAudioSink`, which plays silence until `BUFFER` seconds are ready (`settle`, again after running dry); the sink is thrown away on `clear()` (restarting a stopped `QAudioSink` leaks its PulseAudio stream) and when the default output changes (`_outputs_changed`, `outputChanged`, after which `ReadAloud` says the sentence again), since a sink keeps playing on the device it was made for; `processedUSecs` minus `LATENCY` says which uid and word is audible. The controller queues `lookahead_chars` of text ahead and splits the sentence it starts on at its commas (`Utterance.split`) so the first sound comes quickly. `SpeechdEngine` wraps `QTextToSpeech("speechd")` (sentence-level only). `read_aloud.ReadAloud` feeds `engine.lookahead` sentences ahead (uids are `_first_uid + index`), drives `ReaderView.set_speech`/`follow_speech` (which waits `FOLLOW_PAUSE` after the user scrolls), falls back to speechd for the session when Kokoro fails, and owns the `ReadAloudBar` under the reader (`MainWindow.reading` wraps the two). Replies are split into blocks in the page (`speechBlocks` in `transcript.html`, KaTeX swapped for its TeX) and highlighted by `speakHighlight`. Skip silence (`audio_cache.skip_silence`, Kokoro only: `Engine.skips_silence`) trims a sentence's quiet edges and caps pauses inside it, on both cached and live audio before any `stretch`, moving the tokens with the cuts; jobs carry the flag, so toggling it requeues like a speed change. Settings: `tts_engine`, `tts_voice:<engine>`, `tts_speed`, `tts_skip_silence`. Colab rendering: `colab_render.py` (Qt-free; its docstring is the design) drives a Colab GPU through the `colab` CLI (sessions in our own `--config`, `<data>/colab/sessions.json`, named `study-reader-tts-*`). `RenderDialog` (in `render_dialog.py`) queues a book as `<data>/colab/requests/<key>.json` (sentence keys are `audio_cache.sentence_key(voice, text)`, so any change to the spoken text or voice is just a miss), and `ColabRender` starts the watcher (`python -m study_reader.colab_render`, detached and single by a lock, so it outlives the app; `MainWindow` resumes it at startup unless a `failed` file says why it gave up; **Stop rendering** stays enabled whenever a session is still written down, and a successful stop deletes `failed`). The watcher first copies in what the old Drive notebook finished for the book (the request's `drive` folder), then runs `colab new` (the session name is saved before the call, and a session in our config it doesn't know about is adopted or stopped, so a start cut short is never left running), uploads only the sentences with no audio here at that speed, and starts `assets/kokoro_render.py` in the background on the VM (`RUN_SH` installs Kokoro in a Python 3.12 venv first). It then polls with `colab exec` snippets (`STATUS`; `colab exec` exits 0 even when the code raises, so results come back after `MARK`), `colab download`s finished `part-<run>-NNNN.opus` + `.json` (`[speed, start, samples, Kokoro tokens]`, tokens aligned by the app) straight into `data_dir()/audio/<book_key>` (audio before index), and runs `colab stop` when the queue is empty, or on a `stop` file or a failure. `state.json` is the dialog's view of it, and `ColabRender.synced` brings the open book's cache up to date (`AudioCache.refresh` reads only new or changed index files, through `tts_engines._cache_for`). A book queued again stops its old run on the VM at the next sentence (`Superseded` in `kokoro_render.py`), and the old run's finished parts are still downloaded. Tests use `FakeColab` (a folder as the VM, where the real snippets run), and conftest stubs `start_watcher`. Parts the old Drive notebook made (`part-NNNN`) are still copied from `tts_colab_folder` on `open_book` (`render_dialog.AudioSync`, `audio_cache.sync`, which touches only those names). The Kokoro worker serves cache hits through `job_audio` (WSOLA `stretch` when the speed differs), loading the model only on a miss. Kokoro's own speed drops words above `NATIVE_SPEED` (1.3), so `synthesize` and `render_speed` make audio at most that fast and `stretch` the rest; when a book finishes, `colab_render.prune` deletes its parts that were made at another speed and have since been redone. With a cache the controller starts at a whole sentence and doesn't split it. Tests replace `tts_engines.make_engine` with a fake engine, and conftest stubs `KokoroEngine.warm` so opening a book never starts Kokoro.

**Phone app and sync:** `android/` is Study Practice, an Android companion (Kotlin, its own `pixi.toml`; see `android/CLAUDE.md`) for practicing questions. `phone_sync.py` (Qt-free; its docstring is the format) syncs through a shared Syncthing folder where each side writes only its own files: the desktop rewrites `desktop/snapshot.db` (`SNAPSHOT_SCHEMA`: questions, decks, books with section roots and starts, `question_groups` id, kind and tags, the attempt log, the practice settings, `acks`, and `meta` with `schema` 2, `SNAPSHOT_VERSION`, below which the phone refuses a snapshot) when `_fingerprint` changes (in the app on a thread with its own read-only connection, one write at a time, `PhoneSync.wait()` on quit) and mirrors `media_dir()` to `desktop/media/`; the phone writes immutable `phones/<device>/<batch>.json` event batches (`FORMAT` 2, each event naming its `question`: attempt, suspend, flag, bury, and reward events: xp, achievement, goal, freeze_spent, freeze_earned; format 1 batches, saying `card` and `review`, are still read: `FORMATS`, `OLD_EVENT_TYPES`). `import_batches` applies each event once and each batch whole or not at all (`Database.transaction`; `phone_events`, by id; `phone_batches` become the snapshot's acks, after which the phone deletes the files and stops replaying their events). Phone attempts are logged with source `practice` (so they count against the new-question cap) and replayed through FSRS at their own time; one older than the question's last attempt rebuilds the question from its log (`rebuild`; `_introduced` keeps `was_new` on the right attempt). Rewards are computed on the phone and merged (`_apply_reward`, achievement keys through `gamify.achievement_key`), never recomputed. `phone_sync_dialog.PhoneSync` runs it at startup, every two minutes and on close (`MainWindow.phone_sync`), and asks for new numbers for the calculation questions the phone practiced. The phone shows the same `practice.html` (with `window.PracticeApp` as its bridge, `html.mobile` styles, data-driven `actions`/`links`/`flag`), so question rendering changes reach both; desktop-only behavior in `practice.html` must stay behind the existing defaults. Snapshot schema changes need the Kotlin side (`SyncStore.SNAPSHOT_SCHEMA`, and `SNAPSHOT_VERSION` with `SyncStore.SCHEMA` when old snapshots can't be read) too.

**Documents:** `document.py` wraps PyMuPDF for both PDF and EPUB. EPUBs are laid out at a fixed size (`REFLOW_WIDTH/HEIGHT/FONT`) so page numbers stay stable across runs, which matters because snippet rects and page numbers are persisted. Books are identified by content hash (`file_hash`), so a moved file maps back to the same library entry. `Document.words` (and `_lines`, in the same order, with blocks numbered alike) are in reading order, which selection and read-aloud rely on: `reading_order` keeps the PDF's block order except that a block goes after blocks starting `JUMP_LINES` lines above it (only within its own column when `_in_columns` finds a gutter; small jumps are left alone because math is drawn a glyph at a time) and margin labels (`margin_blocks`) go before the text beside them. Reflowed EPUBs and web snapshots keep their order. Persist rects, never word indices, since this order can change. `Document.links` gives a page's internal links (named destinations are resolved with `resolve_link`, since PyMuPDF leaves their points in bottom-up PDF coordinates) plus `footnote_refs`: unlinked raised markers matched to a line lower on the page that starts with the same small marker. Many PDFs point links only at the top of a page, so `Document.target` lazily (only on hover/click, since reading another page is slow) refines a link's point from its `hint`: a footnote marker finds the footnote with the same marker, a back-link the in-text marker, "Figure 2.1" its caption (bold first). Chromium writes named destinations without the page margins, so for web snapshots (`creator` "Study Reader") `WEB_MARGINS` is added back. Cross-references from headings or into the contents pages are `quiet` (no pill). `link_target` extracts the text a link points at; `ReaderView` draws a pill on each link (violet for footnotes, fainter for cross-references), shows the target as a tooltip, and clicking follows the link with a back stack (`go_back`).

**Web pages:** `web_import.py` (Qt-free) turns a URL into an `Article` of `Section`s: LessWrong/Alignment Forum/EA Forum (`FORUMS`) through their GraphQL API (posts + top comments, sequences, wiki pages with their tabs, called "lenses" in the API), anything else through `readability`. `_absolute_links` keeps in-page `#fragment` links relative so the printed PDF links footnotes internally. `build_html` makes one printable document; math from any source is normalized to `<span class="math" data-tex>` and re-typeset by bundled MathJax SVG (`assets/mathjax/`), with the TeX also printed nearly invisibly in the flow (`.tex-src`) because that is the only math text that extracts cleanly and in reading order. `web_render.WebImporter` fetches in a thread, prints with `QWebEnginePage.printToPdf` at `REFLOW_WIDTH×HEIGHT`, then `finish_pdf` adds metadata and a TOC by searching for each heading. The snapshot then opens through `open_book`; `books.source_url` maps a URL back to its snapshots. **Fetch a fresh copy** (`MainWindow.refetch`) swaps the new file into the same `books` row (`replace_book_file`: new hash/path, base session dropped, `ChatWorker.forget_base`) and deletes the old snapshot, so chats and notes stay. Failed or cancelled imports (`WebImporter.cancel`) delete the files they wrote. Tests stub `web_import.http_get`.

**Persistence:** `db.py` is plain `sqlite3` (books → chats → messages → snippets; decks → questions ← question_groups, attempts, question_rewrites; the Make with Claude draft tables; plus a key/value `settings` table). Writes go through `with self.conn:` (which commits on exit even when nested, except inside `Database.transaction()`, where such blocks become savepoints and everything commits or rolls back together), so internal helpers that are part of a larger write (`_ensure_deck`, `_insert_group`, `_insert_question`, `book_deck`) don't open their own. The database runs in WAL mode. Edits never delete attempted questions: `update_question_group` only adds questions for blanks or sides the edit introduces and drops only never-attempted questions whose blank or side was removed; removing a book or chat keeps attempted questions (`book_id`/`message_id` become NULL). `attempts.was_new` marks introductions (first attempts and attempts after Forget), which the daily new-question cap counts. The schema is `CREATE TABLE IF NOT EXISTS`. For new columns on existing tables, add the column to `SCHEMA` and an `ALTER TABLE` step in `Database._migrate` (see the `chats.model` migration and its test; `test_fresh_database_needs_no_migration` fails if a fresh database runs an ALTER). Databases from before the terminology rename are renamed in place by `Database._rename_old_schema` before `SCHEMA` runs (`TABLE_RENAMES`: cards, card_notes, reviews, card_rewrites; `COLUMN_RENAMES`: note_id, card_id, the quiz index `question` → `position`, last_review, reviewed_at; `OLD_INDEXES` dropped), after a one-time copy to `<stem>.before-rename.db` (`BACKUP_SUFFIX`) beside it; `_migrate_terms` then renames settings keys (`SETTING_RENAMES`, e.g. `srs_new_per_day`, `review_panel`), attempt source `review` → `practice` and the kinds in Make with Claude's stored specs. Snippet and note `rects` are JSON in PDF page points; a passage selected across pages starts on its `page`, and its rects on later pages carry their page as a fifth number (`db.passage_pages`, `db.last_page`; loaded rows get `last_page`), so marks, flashes, page labels, the passage's "from pages N–M" for Claude and quiz questions' page range cover every page. Data lives in `$STUDY_READER_DATA` or `$XDG_DATA_HOME/study-reader`.

**QtWebEngine:** `__main__.configure_webengine` forces `--disable-gpu` (blank transcript on some Wayland compositors) unless `STUDY_READER_WEB_GPU=1`.
