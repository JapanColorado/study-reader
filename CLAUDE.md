# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Study Reader is a PySide6 desktop PDF/EPUB/web-page reader (Linux only) where selected passages or screenshot regions are sent to per-snippet Claude chats that all share the whole book as context. See README.md for user-facing behavior and keyboard shortcuts.

## Commands

Pixi manages the environment; `PYTHONPATH` is set to `src/` by pixi activation, so run everything through `pixi run`.

```sh
pixi run app [book.pdf | URL]      # launch (library screen, or open a book or web page)
pixi run test                      # pytest -q tests
pixi run pytest -q tests/test_core.py::test_first_chat_primes_then_forks   # single test
pixi run check-claude              # live priming+forking check; makes real Claude requests
```

Tests never hit Claude: `FakeClaude` in `tests/test_core.py` monkeypatches `claude_client.run_turn` and `claude_client.session_exists`. Test PDFs/EPUBs are generated on the fly in `tests/conftest.py`.

## Architecture

**Shared book context via session forking** (the core idea, spread across `claude_client.py` and `chat_service.py`):
- Claude is reached through the Claude Agent SDK (`query()`), which drives the local `claude` CLI and its login. Each book gets its own session working directory (`<data>/sessions/book-<id>`), since SDK sessions are scoped by `cwd`.
- The first question for a book "primes" a base session containing the full extracted text (`[[page N]]` markers). Each new chat resumes that base session with `fork_session=True`; follow-ups resume the chat's own session without forking.
- `ChatService.ask` decides the route: chat session exists → resume it; otherwise `ensure_base` (re-priming if the base session was pruned) then fork, replaying saved DB history as a transcript if the chat's own session was lost.
- Regenerate / edit truncate the chat in the DB, then branch: each assistant message stores its `session_id` and `session_uuid` (last transcript entry), and the job resumes that session with `resume_at` (SDK `resume_session_at`) plus `fork=True`. With no usable branch point the job falls back to fork-from-base plus history replay, and `ask` retries that way if the branch point fails to load.
- Books over `MAX_BOOK_TOKENS` (estimated at 3 chars/token), or whose priming fails with a "too long" error, switch to `context_mode="partial"`: no base session, and each question carries a `text_window` of pages around the current page.
- Chat titles: a chat started from the composer is named after its first question until its first reply lands; then `ChatPanel._name_chat` asks `ChatService.title` for a short title (`cc.chat_title`: a fresh, bookless Haiku session under `<data>/sessions/titles` with `TITLE_PROMPT` as its system prompt). The `titled` event only applies if the chat wasn't renamed meanwhile; failures are silent. Quiz chats keep their given titles.
- `_options()` deliberately strips all tools, MCP servers (including claude.ai connectors via `ENABLE_CLAUDEAI_MCP_SERVERS=false`), and setting sources, and uses `max_turns=1`. `_prefer_subscription_login()` removes `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN` from the environment unless `STUDY_READER_USE_API_KEY=1`.
- A resumed or forked session keeps the system prompt it was created with; the `system_prompt` passed on later calls is ignored. So `SYSTEM_PROMPT` edits only reach newly primed books. Put behavior that must apply everywhere in `READER_INSTRUCTIONS`, which `build_blocks` sends with every question.

**Threading:** `ChatWorker` runs `ChatService` on a dedicated asyncio loop in a daemon thread. `ChatService` is Qt-free and reports through an `emit(name, *args)` callback; `ChatWorker._emit` maps names to Qt signals (`status`, `base`, `delta`, `done`, `failed`) that `ChatPanel` connects to. Keep new events in both places. Persisting results (session ids, `context_mode`, messages) happens on the GUI side in `ChatPanel`, not in the service.

**UI modules:**
- `main_window.py` wires everything: the navigation rail (`nav.py`'s `NavRail`, with the Settings menu at its foot) beside a center `QStackedWidget` of pages (`MainWindow.pages`: home, library, review, cards, stats, and "book", the reader), the reader's toolbar (shown only while reading), TOC dock, highlights → chat navigation. `show_page` switches pages; the open book stays open behind the others (`close_book`, `Ctrl+W`, closes it), and `reading` means the reader is on screen, which gates the toolbar, book actions and right-hand panels. The card browser (`CardBrowser(embedded=True)`, a `QMainWindow` used as a widget, its menu bar inside the page) and statistics (`StatsWindow(window=False)`) are made on first visit into `_Page`s. While Cards is shown, the window's Open web page action is disabled so the browser's `Ctrl+Shift+O` wins; page shortcuts are `Alt+1`–`6` because the browser uses `Ctrl+digits` for flags.
- `home_view.py`'s `HomeView` renders `assets/home.html` from `dashboard.home()` (Qt-free `dashboard.py`: per-book counts `book_counts`, the review page's deck list `deck_rows`, `reading`, `heat`, `forecast`). Covers are first-page PNGs in `<data>/covers/<hash>.png` (`covers.py`); the Library draws them a turn of the event loop at a time. `assets/app.css` (panels, buttons, the due/new colors) and `assets/progress.js` (rewards row, calendar heatmap, forecast bars) are shared by `home.html` and `review.html`. Theme keys `new`/`new_soft` (blue: new cards), `success_soft`, `rail` and `shadow` reach pages as CSS variables like the rest.
- `reader_view.py` is a custom `QAbstractScrollArea` that renders pages with PyMuPDF, handles word-level text selection, region screenshots, persistent highlights, and the flash-on-jump effect.
- Find (Ctrl+F): `book_search.py` (Qt-free) folds each page's words (`Document.search_words`: reading order if `words` has already worked it out, else PyMuPDF's, since ordering is most of the cost) into one string (case, accents, ligatures, curly quotes folded; line-break hyphens joined), keeping each word's offsets and, where folding changes a word's length, a char map, so matches turn back into per-line rects (partial words cut in proportion) and printed context. `BookSearch` scans from the current page to the end, then from the start, a time-boxed `step` at a time (a step never crosses the wrap, so its matches are inserted together into the page-ordered list); `SearchIndex` caches folded pages per open book. `find_view.BookFind` runs it on a zero-interval `QTimer`, owns the `FindBar` (floating in the reader's viewport) and `FindResults` (a `QListView` swapped for the TOC in the sidebar's `side_stack` while active; `MainWindow._sync_sidebar`), and paints matches through `ReaderView.set_find`/`show_match`. `ReaderView.escapePressed` (Escape with no selection) closes it.
- `chat_panel.py` holds the chat list, composer, and per-chat model selector, and builds `Job`s for the worker.
- `calculator.py` has a Qt-free `Calculator` (safe `ast`-based evaluator; never `eval`; ints and decimals stay exact as `Fraction`s, functions give floats) and the `CalculatorPanel` that shares the right-hand `QStackedWidget` slot with `ChatPanel` (F10/F11 are mutually exclusive). The panel's history and input are `assets/calculator.html`: a MathLive math field (bundled in `assets/mathlive/`) talking to `_Bridge` over `QWebChannel`. `calc_latex.py` turns the field's LaTeX into plain expressions (inserting implied multiplication) and results back into LaTeX/fractions. History is per book in the `calculations` table (`expr` evaluated, `latex` as typed); `ans` and variables are restored from stored values, not by re-evaluating.
- `transcript_view.py` is a `QWebEngineView` loading `assets/transcript.html` (markdown-it + KaTeX, bundled offline in `assets/`). Snippet clicks come back as `jump:<snippet_id>` navigations intercepted in `_Page.acceptNavigationRequest`.
- Visualizations: `READER_INSTRUCTIONS` tells Claude to write ```` ```visualization <title> ```` fences of self-contained HTML/JS. `transcript.html` renders each fence in an `<iframe sandbox="allow-scripts" srcdoc>` built by `vizDoc()`. That doc carries a no-network CSP, the theme as CSS variables plus `vizTheme`, and d3/Chart.js inlined from `assets/viz/` when the code references them (sandboxed frames can't load `file://`). Frames `postMessage` their size (`vizSize`, with the width it was measured at) and `assets/vizfit.js`'s `VizFit` fits each into the panel: laid out narrower when too tall (plots drawn to the width shrink with it), then scaled. During streaming, fences show a placeholder. `viz://open/<n>` opens `VisualizationWindow` with `vizDoc(n, true)`, fetched via `runJavaScript` as JSON: `assets/vizwindow.html` is a toolbar over a full-window frame whose doc runs `vizWindowMode` (inlined by `vizDoc`), which moves the controls into a pinned dock outside the body, fits the body and zooms it with CSS `zoom`; the toolbar talks to it by `postMessage`, and F11/Escape come back as `viz://fullscreen`/`viz://normal` navigations.
- Quizzes: `READER_INSTRUCTIONS` also defines ```` ```quiz <title> ```` fences of JSON (types choice, truefalse, numeric, free, and self-rated flashcard; flashcard requests are quizzes of flashcards). `quiz.py` (Qt-free) parses them (forgiving undoubled LaTeX backslashes), grades choice/true-false/numeric answers locally (numeric through `Calculator`), and builds the grading prompt and the `<quiz_answers>` context (`Job.context`) sent with later questions. `ChatPanel` replaces each fence with a `#<index>` placeholder plus parsed data that `transcript.html` renders; answers come back over a `QWebChannel` (`_QuizBridge`) and are stored in `quiz_answers`. Free responses are graded by `ChatService.grade` as a `detached` job that always forks (at the quiz reply's `session_uuid`), so the chat's own session never sees it. `assets/mathfield.js` holds the MathLive setup shared with the calculator.
- Spaced repetition: every quiz question is a review card. `srs.py` (Qt-free) makes cards from a reply's quiz fences when `ChatPanel` saves it (`add_quiz_cards`; one per `message_id, quiz, question`, in the book's deck, `books.deck_id`, made by `Database.book_deck`), and schedules them with the `fsrs` package (`cards.fsrs` holds the `fsrs.Card` JSON, `stage` 0 = new, else `fsrs.State`; `stability`/`difficulty`/`last_review` mirror it for browsing, so write schedules through `srs.schedule_columns` (`srs.new_schedule_columns` for new cards); retrievability from those columns is `srs.recall`; `reviews` logs each rating with its `duration`). `srs.scheduler(db)` uses the stored FSRS weights (`srs_parameters`, from Anki or `srs.fit` over `srs.review_logs`, which needs PyTorch, installed CPU-only by pixi) and desired retention. The first answer in the chat is a card's first review (`answered_in_chat`, verdict → rating; flashcards are rated directly); retakes don't count. Review-state cards are due for the whole day they fall on (days roll over at 4 am); new cards are capped per day across all decks (`srs_new_per_day`). Deleting a reply drops its never-reviewed cards; reviewed ones outlive it with `message_id` NULL (`Database._drop_new_cards`). `review.py`'s `ReviewPanel` (rendered in `assets/review.html`) is the fourth right-hand panel for the open book (`book_id` scope), and a second instance (`all_books=True`) fills the center from the library's **Review** button with a deck picker (`deck_id` scope, subtree via `db.SUBTREE`). Free responses are graded by Claude only in the chat; in review they are self-rated like flashcards (an optional answer box, then the model answer and rubric beside it; `selfRated` in `review.html`), and `READER_INSTRUCTIONS` keeps them as a last resort. Question rendering is shared by `transcript.html`, `review.html` and `cardview.html` in `assets/quiz.js`/`quiz.css`. `srs.backfill` makes cards once for quizzes written before cards existed. New numbers: after a numeric or free-response card's review (or first answer in the chat), `review.VariantMaker` (one, made by `MainWindow`, handed to `ChatPanel` and both review panels) asks for the problem's next version with fresh givens (`variants.request`, in a fresh bookless session to keep it cheap, via `ChatWorker.submit_variant`, `varied`/`variantFailed` events) and stores it in `cards.variant` (`{"skip": true}` when Claude says there is nothing to vary). Quiz questions carry `"varies"` (from `READER_INSTRUCTIONS`, or the browser editor's checkbox); `false` means never ask, `true` tells Claude to rephrase rather than skip, and only unmarked older cards get the one-time check; the `variants` setting (`variants.ENABLED_SETTING`) turns new versions off everywhere, and review and the phone snapshot then show the cards' own questions; review shows `variants.question(card)`, pinned while the card is up. Edits that change a card's data drop its variant.
- Section and concept tags: `add_quiz_cards` tags each card `Book::Chapter::Section` (`srs.section_tag`, parts cleaned by `cardmodel.tag_part`) from the book's TOC, stored as JSON in `books.toc` by `srs.learn_toc` (called in `open_book`; at startup `MainWindow._learn_tocs` opens books with quiz cards but no stored TOC). The page comes from the snippet or from `messages.page_from`/`page_to` (a quiz on a page range gets the common prefix of both ends' section paths); learning a TOC the first time tags that book's existing cards. Back matter (Summary, Exercises…) that a TOC nests in a chapter's last section is filed under the chapter (`srs._entry_path`), and a question may name the section it practices (`"section": "6.4"`, matched by `srs.find_section`), which wins over its page, so end-of-chapter exercises land in their sections. Questions may carry their own `"tags"` (concept tags, cleaned by `cardmodel.clean_tag`); `srs.tags_context` sends the user's existing concept tags (`<existing_tags>`, capped) in `Job.context` with every question so Claude reuses them. Both review panels can narrow to a book or a section (`srs.sections` builds the per-book tree in reading order, by each section's TOC start; `counts`/`next_card`/`next_due` and `Database._scope` take `tag=`, matching the tag and its children); a narrowed session shows due and new cards only. Books' own decks are left out of the deck picker unless a user deck sits under them. The browser sidebar orders section tags by page and has a tag filter (`Sidebar.filter_tags`).
- Quiz revisions: a quiz fence may name the quiz it `"revises"` (by title; `quiz.revised_quiz` falls back to the chat's latest quiz), and each question the 1-based number of the old question it replaces. `add_quiz_cards` moves those cards to the new reply (`Database.relink_card`) and rewrites their notes (`update_card_note`, merging tags), so review history stays; then `Database.drop_new_quiz_cards` removes the old quiz's remaining never-reviewed cards. The **Revise…** button (`_QuizBridge.revise` → `ChatPanel.revise_quiz`) sends `quiz.revise_request`; `ChatPanel._revisions` maps old quizzes to their revising reply so `transcript.html` dims them with a "Show the revision" link. Regenerating a revision reply loses the cards it took over that were never reviewed.
- Rewards: `gamify.py` (Qt-free) gives the Review panel XP and levels, a combo (cards in a row without a `COMBO_PAUSE`; it raises the XP multiplier), a daily goal, streaks with streak freezes, achievements, quick sessions (`Session.limit` "cards"/"time") and session summaries. XP never depends on the rating, so it never pays to rate a card better than it went. Streaks and today's count come from the review log; XP, freezes and unlocked achievements live in the `gamify_state` setting (made from the log the first time). `ReviewPanel` sends what a review earned to `celebrate()` in `review.html` (toasts, `assets/confetti.js`); the `gamify` setting hides it all.
- Decks and notes: cards belong to `decks` (full `A::B` names; parents have rows) and to `card_notes` (`kind` + JSON `fields`, Anki-style tags ` a b `). `cardmodel.py` (Qt-free) defines the kinds (quiz, basic, reverse, cloze, occlusion; a flashcard is always a basic note, even from a chat quiz, via `cardmodel.note_for_question`, and quiz notes hold only answered types; `Database._migrate` moves old quiz-note flashcards over), which cards a note makes (`card_ords`), and each card's question JSON (`card_data`, cached in `cards.data` and remade by `Database.update_card_note`); cloze and occlusion are self-rated types like flashcards (`cardmodel.SELF_RATED`, `quiz.js` `SELF_RATED`). Card text is Markdown that may hold inline HTML (`q.html`), rendered by `renderMarkdown(…, rich)` in `markdown.js`, which rebuilds it from an allowlist of tags, attributes and URL schemes (pages with web channels must never run card scripts) and points relative image paths at `media_dir()`. Databases from before decks are migrated by `Database._migrate_cards_to_notes`, which rebuilds `cards` with foreign keys off; indexes live in `INDEXES`, applied after migrations.
- Card browser: `browser.py`'s `CardBrowser` window (made lazily by `MainWindow.show_browser`) runs `search.py` (Qt-free Anki-style query → SQL over `search.FROM`; `SORTS` per column) into `CardTableModel`, which reads rows a chunk at a time. Column widths are worked out by `CardBrowser._fit_widths` on every viewport resize: compact columns fit their header and `SAMPLES`, `FLEX_COLUMNS` share the rest by weight within bounds; a column the user drags keeps its width (`browser_widths`), and a dragged column's new place becomes the saved column order. `card_editor.py` holds the `NoteEditor` (autosaved after a pause) and `AddDialog`. Switching a question's type carries its answer over (`NoteEditor._carry_answer`); an edit that can't be saved yet is kept per note in `CardBrowser._drafts` and shown again when the note is, so leaving the card doesn't revert it. `cardview.html` shows read-only card sides (the preview, and Claude Conversion's review). `stats.py`/`stats_view.py`/`stats.html` are the Statistics window.
- Claude Conversion: `convert.py` (Qt-free) builds batched requests (cards as JSON, their images attached) and parses Claude's proposals into the `conversions` table; `convert_dialog.py`'s `ConversionManager` sends them through `ChatWorker.submit_conversion` (`converted`/`convertFailed` events; at most `CONVERSIONS_AT_ONCE` run together, model `sonnet`, a fresh bookless session per batch) and `ConversionDialog` shows them. `convert.record` keeps cards whose proposal is a needless flashcard (`_needless`: a quiz question other than a free response, or the same text). A proposal may split a card into up to `MAX_SPLIT` questions (`proposal` is then a JSON list; read it through `convert.questions`). Accepting moves the card to a new note (`Database.move_card_to_note`; basic for a flashcard, else quiz), keeping its schedule; a split's other questions become new cards in its deck, book and page with its tags. The original (and `added`, the split's new card ids) is kept in the row for `convert.revert`, which drops added cards never reviewed.
- Anki migration: `anki_import.py` (Qt-free) reads a temp copy of `collection.anki2` (decoding the protobuf blobs it needs), maps note types to kinds by their fields, converts field HTML to Markdown (`to_markdown`), imports schedules, revlog (source `anki`), media and FSRS parameters; `cards.anki_id`/`card_notes.anki_id` make re-runs skip what's there. `anki_dialog.py` is its dialog. It never writes to Anki.
- Notes: `notes.py` has Qt-free search/Markdown export and the `NotesPanel`, the third panel in the right-hand `QStackedWidget` (`MainWindow.right_panels` maps `books.right_panel` names to their toggle actions; at most one is shown). Cards render in `assets/notes.html` and edits come back over `QWebChannel`. Notes live in the `notes` table (passage text + rects, like snippets) and are passed to `ReaderView.set_highlights` alongside snippets; a mark holding notes draws in blue. They are never sent to Claude. `assets/markdown.js` holds the Markdown + KaTeX rendering shared with `transcript.html`.
- Read aloud: `speech_text.py` (Qt-free) turns text into what is spoken (`tex_to_speech`, `math_symbols`, `speak_word` abbreviations), splits sentences (`ends_sentence`), and maps an engine's timed tokens onto the spoken text (`align_tokens`); an `Utterance` keeps its page rects and `marks` (spoken char range → page rects) so a word timing lights the right word. `speech_pages.BookText` (Qt-free, per `Document`, lazy a page at a time on the GUI thread) yields a book's sentences from a word on, skipping running headers/footers/page numbers (edge lines repeating on p±1/p±2), footnotes (`footnote_starts`: a raised marker opening a row, so numbered steps, bullets and wrapped exponents aren't taken for one and everything below them skipped; footnote links, numbers glued after punctuation) and captions, joining hyphenation, finding headings by font size (`Document.body_size`) and speaking web snapshots' tiny `.tex-src` runs as math. `tts_engines.py`: `KokoroEngine` runs Kokoro in a spawned process (`kokoro_worker`, niced, exits when the app does; started by `warm()` when a book opens, since loading takes seconds). Jobs carry a generation (shared `Value`) so cleared ones are skipped; results come back through a listener thread and `_Bridge` signals into a `PcmQueue` pulled by a `QAudioSink`, which plays silence until `BUFFER` seconds are ready (`settle`, again after running dry); the sink is thrown away on `clear()` (restarting a stopped `QAudioSink` leaks its PulseAudio stream) and when the default output changes (`_outputs_changed`, `outputChanged`, after which `ReadAloud` says the sentence again), since a sink keeps playing on the device it was made for; `processedUSecs` minus `LATENCY` says which uid and word is audible. The controller queues `lookahead_chars` of text ahead and splits the sentence it starts on at its commas (`Utterance.split`) so the first sound comes quickly. `SpeechdEngine` wraps `QTextToSpeech("speechd")` (sentence-level only). `read_aloud.ReadAloud` feeds `engine.lookahead` sentences ahead (uids are `_first_uid + index`), drives `ReaderView.set_speech`/`follow_speech` (which waits `FOLLOW_PAUSE` after the user scrolls), falls back to speechd for the session when Kokoro fails, and owns the `ReadAloudBar` under the reader (`MainWindow.reading` wraps the two). Replies are split into blocks in the page (`speechBlocks` in `transcript.html`, KaTeX swapped for its TeX) and highlighted by `speakHighlight`. Settings: `tts_engine`, `tts_voice:<engine>`, `tts_speed`. Colab rendering: `colab_render.py` (Qt-free; its docstring is the design) drives a Colab GPU through the `colab` CLI (sessions in our own `--config`, `<data>/colab/sessions.json`, named `study-reader-tts-*`). `RenderDialog` (in `render_dialog.py`) queues a book as `<data>/colab/requests/<key>.json` (sentence keys are `audio_cache.sentence_key(voice, text)`, so any change to the spoken text or voice is just a miss), and `ColabRender` starts the watcher (`python -m study_reader.colab_render`, detached and single by a lock, so it outlives the app; `MainWindow` resumes it at startup unless a `failed` file says why it gave up). The watcher first copies in what the old Drive notebook finished for the book (the request's `drive` folder), then runs `colab new` (the session name is saved before the call, and a session in our config it doesn't know about is adopted or stopped, so a start cut short is never left running), uploads only the sentences with no audio here at that speed, and starts `assets/kokoro_render.py` in the background on the VM (`RUN_SH` installs Kokoro in a Python 3.12 venv first). It then polls with `colab exec` snippets (`STATUS`; `colab exec` exits 0 even when the code raises, so results come back after `MARK`), `colab download`s finished `part-<run>-NNNN.opus` + `.json` (`[speed, start, samples, Kokoro tokens]`, tokens aligned by the app) straight into `data_dir()/audio/<book_key>` (audio before index), and runs `colab stop` when the queue is empty, or on a `stop` file or a failure. `state.json` is the dialog's view of it, and `ColabRender.synced` reloads the open book's cache. Tests use `FakeColab` (a folder as the VM, where the real snippets run), and conftest stubs `start_watcher`. Parts the old Drive notebook made (`part-NNNN`) are still copied from `tts_colab_folder` on `open_book` (`render_dialog.AudioSync`, `audio_cache.sync`, which touches only those names). The Kokoro worker serves cache hits through `job_audio` (WSOLA `stretch` when the speed differs), loading the model only on a miss. Kokoro's own speed drops words above `NATIVE_SPEED` (1.3), so `synthesize` and `render_speed` make audio at most that fast and `stretch` the rest; when a book finishes, `colab_render.prune` deletes its parts that were made at another speed and have since been redone. With a cache the controller starts at a whole sentence and doesn't split it. Tests replace `tts_engines.make_engine` with a fake engine, and conftest stubs `KokoroEngine.warm` so opening a book never starts Kokoro.
- `theme.py` has a global `theme()` singleton (light/dark/system plus "dark pages" recoloring via `darken_page`) that emits `changed`, and draws line icons from inline SVG.

**Phone app and sync:** `android/` is an Android companion (Kotlin, its own `pixi.toml`; see `android/CLAUDE.md`) for reviewing cards. `phone_sync.py` (Qt-free; its docstring is the format) syncs through a shared Syncthing folder where each side writes only its own files: the desktop rewrites `desktop/snapshot.db` (cards, decks, books with section roots and starts, card note tags, the review log, the review settings, `acks`) when `_fingerprint` changes and mirrors `media_dir()` to `desktop/media/`; the phone writes immutable `phones/<device>/<batch>.json` event batches (review, suspend, flag, bury, and reward events: xp, achievement, goal, freeze_spent, freeze_earned). `import_batches` applies each event once (`phone_events`, by id; `phone_batches` become the snapshot's acks, after which the phone deletes the files and stops replaying their events). Phone reviews are logged with source `review` (so they count against the new-card cap) and replayed through FSRS at their own time; one older than the card's last review rebuilds the card from its log (`rebuild`). Rewards are computed on the phone and merged (`_apply_reward`), never recomputed. `phone_sync_dialog.PhoneSync` runs it at startup, every two minutes and on close (`MainWindow.phone_sync`), and asks for new numbers for the calculation cards the phone reviewed. The phone shows the same `review.html` (with `window.ReviewApp` as its bridge, `html.mobile` styles, data-driven `actions`/`links`/`flag`), so card rendering changes reach both; desktop-only behavior in `review.html` must stay behind the existing defaults. Snapshot schema changes need the Kotlin side (`SyncStore.SNAPSHOT_SCHEMA`) too.

**Documents:** `document.py` wraps PyMuPDF for both PDF and EPUB. EPUBs are laid out at a fixed size (`REFLOW_WIDTH/HEIGHT/FONT`) so page numbers stay stable across runs, which matters because snippet rects and page numbers are persisted. Books are identified by content hash (`file_hash`), so a moved file maps back to the same library entry. `Document.words` (and `_lines`, in the same order, with blocks numbered alike) are in reading order, which selection and read-aloud rely on: `reading_order` keeps the PDF's block order except that a block goes after blocks starting `JUMP_LINES` lines above it (only within its own column when `_in_columns` finds a gutter; small jumps are left alone because math is drawn a glyph at a time) and margin labels (`margin_blocks`) go before the text beside them. Reflowed EPUBs and web snapshots keep their order. Persist rects, never word indices, since this order can change. `Document.links` gives a page's internal links (named destinations are resolved with `resolve_link`, since PyMuPDF leaves their points in bottom-up PDF coordinates) plus `footnote_refs`: unlinked raised markers matched to a line lower on the page that starts with the same small marker. Many PDFs point links only at the top of a page, so `Document.target` lazily (only on hover/click, since reading another page is slow) refines a link's point from its `hint`: a footnote marker finds the footnote with the same marker, a back-link the in-text marker, "Figure 2.1" its caption (bold first). Chromium writes named destinations without the page margins, so for web snapshots (`creator` "Study Reader") `WEB_MARGINS` is added back. Cross-references from headings or into the contents pages are `quiet` (no pill). `link_target` extracts the text a link points at; `ReaderView` draws a pill on each link (violet for footnotes, fainter for cross-references), shows the target as a tooltip, and clicking follows the link with a back stack (`go_back`).

**Web pages:** `web_import.py` (Qt-free) turns a URL into an `Article` of `Section`s: LessWrong/Alignment Forum/EA Forum (`FORUMS`) through their GraphQL API (posts + top comments, sequences, wiki pages with their tabs, called "lenses" in the API), anything else through `readability`. `_absolute_links` keeps in-page `#fragment` links relative so the printed PDF links footnotes internally. `build_html` makes one printable document; math from any source is normalized to `<span class="math" data-tex>` and re-typeset by bundled MathJax SVG (`assets/mathjax/`), with the TeX also printed nearly invisibly in the flow (`.tex-src`) because that is the only math text that extracts cleanly and in reading order. `web_render.WebImporter` fetches in a thread, prints with `QWebEnginePage.printToPdf` at `REFLOW_WIDTH×HEIGHT`, then `finish_pdf` adds metadata and a TOC by searching for each heading. The snapshot then opens through `open_book`; `books.source_url` maps a URL back to its snapshots. **Fetch a fresh copy** (`MainWindow.refetch`) swaps the new file into the same `books` row (`replace_book_file`: new hash/path, base session dropped, `ChatWorker.forget_base`) and deletes the old snapshot, so chats and notes stay. Tests stub `web_import.http_get`.

**Persistence:** `db.py` is plain `sqlite3` (books → chats → messages → snippets; decks → cards ← card_notes, reviews, conversions; plus a key/value `settings` table). Writes go through `with self.conn:` (which commits on exit even when nested), so internal helpers that are part of a larger write (`_ensure_deck`, `_insert_note`, `_insert_card`, `book_deck`) don't open their own. The database runs in WAL mode. Edits never delete reviewed cards: `update_card_note` only adds cards for cloze numbers or sides the edit introduces and drops only never-reviewed cards whose deletion was removed; removing a book or chat keeps reviewed cards (`book_id`/`message_id` become NULL). `reviews.was_new` marks introductions (first reviews and reviews after Forget), which the daily new-card cap counts. The schema is `CREATE TABLE IF NOT EXISTS`. For new columns on existing tables, add an `ALTER TABLE` step in `Database._migrate` (see the `chats.model` migration and its test). Snippet `rects` are JSON in PDF page points. Data lives in `$STUDY_READER_DATA` or `$XDG_DATA_HOME/study-reader`.

**QtWebEngine:** `__main__.configure_webengine` forces `--disable-gpu` (blank transcript on some Wayland compositors) unless `STUDY_READER_WEB_GPU=1`.
